STARTER DECK OWNERSHIP MODEL
- Official starter decks are templates
- On onboarding, user chooses one starter deck
- App duplicates the entire selected deck
- All 100 cards are duplicated with new card IDs
- One NEW user_card_progress row is created per copied card
- The duplicated deck becomes the user's independent deck
- source_deck_id / source_card_id preserve provenance
- User edits never affect official templates or other users
- The unselected starter deck remains available to add later
- Starter duplication must be idempotent and transactional

SESSION / DECK SCOPE
- Multiple decks are NOT mixed within one session
- User studies only the currently selected user-owned deck
- Start Session:
  1. Due review cards from selected deck first
  2. When reviews are cleared, automatically continue into learning cards from same deck
- No separate Review button on Home
- Review vs learning is an internal mode change only
- Combo, current enemy, enemy HP, XP, and battle state continue through the transition
- Brief "Reviews Cleared" feedback may appear

SESSION RESUME
- Pressing START SESSION creates/resumes one session
- Closing the app does NOT automatically complete the session
- Unfinished session remains active
- On return, user can Resume or Finish
- Resume restores:
  - enemy type
  - enemy max/current HP
  - combo
  - session XP
  - session enemy count
  - Daily Goal progress
  - learning draw index
- The unanswered card that was visible at app close is NOT restored
- No answer_event is created for an unanswered card
- Resume draws a fresh next card

FLASHCARD ANSWER UX
- Traditional front/back flashcard
- Show front
- User recalls mentally
- User taps Show Answer
- Back is shown
- User selects Correct or Wrong
- Recall time is measured from front display until Show Answer
- Correct/Wrong selection itself is not the response-time measurement

ACTIVE POOL / MASTERY
- MVP uses Active Pool only
- Active Pool is DERIVED, not stored as a separate table/flag
- Target size: ~30 cards
- Eligible statuses: NEW, LEARNING, FORGOTTEN
- Priority:
  1. FORGOTTEN
  2. existing LEARNING
  3. NEW refill
- Pre-Active Pool removed for MVP
- Outside Pool removed for MVP

Card lifecycle:
NEW -> LEARNING -> LEARNED <-> FORGOTTEN

Mastery rule:
- correct_streak >= 4
- seen_count >= 5
=> LEARNED

LEARNING DRAW / REAPPEARANCE
- Learning draw position is tracked per session
- Review cards do not increment learning draw index
- Correct at draw N:
  - cannot appear in the next 10 Learning draws
  - next eligible draw = N + 11
- Wrong at draw N:
  - must reappear 6-9 Learning draws later
  - forced position is randomly chosen
- If two forced reappearances collide:
  - later reservation shifts forward until a free position is found
- Wrong also sets a cooldown FLOOR: the card cannot be selected again
  before its (possibly collision-shifted) final reserved draw --
  next_eligible_draw_index = forced_reappear_draw_index (the shifted
  final value). The reserved draw is both the earliest eligible draw and
  the forced/guaranteed reappearance draw.
- Queue/cooldown state survives session resume
- This queue is NOT the Active Pool

RETENTION / FSRS
- Use ts-fsrs
- request_retention = 0.90
- enable_fuzz = true
- enable_short_term = true
- FSRS is responsible for memory state and next review scheduling
- Product card_status and internal FSRS state remain separate
- Custom estimator converts Correct/Wrong + behavior into Again/Hard/Good/Easy
- MVP uses rule-based estimator
- Future version personalizes relative response speed by user/card history

Provisional rating logic:
- Wrong -> Again
- Correct + very slow recall -> Hard
- Correct + normal recall -> Good
- Correct + fast recall + seen_count >= 4 + stable recent correct history + previous answer not Wrong -> Easy
- Exact time thresholds remain configurable / TBD

REVIEW QUEUE
- Review queue is fixed when the review portion starts
- Cards that become due afterward are NOT added to the same review portion
- First Wrong:
  - wrong_count = 1
  - move card to back of review queue
- Second Wrong in same review portion:
  - wrong_count = 2
  - card_status = FORGOTTEN
  - review queue item is considered completed
  - card becomes eligible for Learning Active Pool
- Previous FSRS history/state is kept
- After re-mastery, retention scheduling continues from accumulated history
- Review wrong_count survives session resume

BATTLE
- Learning session is represented as battle
- Enemy continuously spawns after defeat
- Session is endless until user explicitly finishes
- 3 enemy types in MVP
- Enemy appearance differs
- Enemy HP differs slightly
- Enemy spawn is random
- No attributes/skills/elements in MVP

Initial enemy HP:
- Enemy A: 90
- Enemy B: 105
- Enemy C: 120

Damage:
- Correct -> damage
- Wrong -> 0 damage and combo reset
- Base damage random integer 24-28
- Small randomness is intentional
- Combo bonus
- Speed bonus
- Critical chance

Combo:
- Consecutive Correct answers increase combo
- Wrong resets combo to 0
- Cap: x10
- Suggested damage bonus:
  x1-2: +0
  x3-4: +2
  x5-6: +4
  x7-8: +6
  x9-10: +8

Speed bonus:
- Max +3 damage
- Exact thresholds TBD/configurable
- Future personalization should use relative response speed

Critical:
- 5% probability
- Final damage x2
- Does not affect memory rating / FSRS
- Strongest visual feedback effect

Visual effects:
- Correct: damage popup, enemy hit reaction, HP decrease
- Combo milestones: visual emphasis at x3/x5/x10
- Speed: brief FAST indicator
- Critical: large CRITICAL text, larger damage number, stronger hit reaction, short flash/shake/particles
- Effects should be short and not slow the learning loop

DAILY GOAL / STREAK
- Daily Goal: defeat 5 enemies
- Avoid displaying a fixed number of required questions
- Goal complete screen offers Continue / Finish
- Streak increases only when Daily Goal is completed
- Simply opening app or answering one card does not preserve streak
- Asia/Tokyo day boundary
- Daily Goal XP and streak must be idempotent: max once per user per JST date

XP / LEVEL
Provisional XP:
- Correct Answer: +2 XP
- Card becomes LEARNED: +15 XP
- FORGOTTEN card becomes LEARNED again: +15 XP
- Enemy Defeated: +20 XP
- Daily Goal Complete: +30 XP
- No direct XP for combo, speed bonus, critical, wrong answer

Provisional level curve:
XP required for next level =
200 + 50 * (current_level - 1)

Examples:
Lv1->2: 200
Lv2->3: 250
Lv3->4: 300
...

XP DATA MODEL
- Current cumulative XP lives on profile state
- Why XP changed is stored in append-only xp_events
- XP events must be idempotent
- Admin adjustments use explicit admin logic

DATA ARCHITECTURE
Three layers:
1. Current state
   - profiles
   - user_card_progress
   - sessions
2. Append-only raw history
   - answer_events
   - xp_events
3. Aggregate/cache
   - daily_user_stats

Raw history is the authoritative audit trail for beta analysis.

RAW ANSWER EVENTS
- One answered card = one append-only answer_event
- Never update/delete normal answer events
- Client generates client_event_id UUID for idempotency
- Retry/double tap with same client_event_id must not double-process
- Raw event should capture at least:
  - user_id
  - card_id
  - deck_id
  - session_id

TRANSACTION / INTEGRITY REQUIREMENTS
Critical multi-table operations are atomic.
Use Postgres transactions / trusted database functions where appropriate.

Important trusted operations:
- duplicate_starter_deck()
- submit_answer()

submit_answer() must atomically handle:
- lifecycle updates
- FSRS state
- review/learning queue state
- battle state
- raw answer event
- session aggregates
- daily aggregates
- XP events
- profile XP/level
- Daily Goal / streak if triggered

If one step fails:
- rollback entire operation
